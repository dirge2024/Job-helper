# 多简历切换功能设计稿

## 背景

当前扩展只在 `chrome.storage.local.userProfile` 中保存一套完整的 `UserProfile`。设置页、插件弹窗、信息侧栏、普通填充、AI 扫描填充、AI 框选补填、简历解析、JSON 备份与 WebDAV 同步都读取这同一套资料。

用户需要保存多套彼此独立的求职资料，并在投递前切换。不同简历之间不共享基本信息；若需要复用，用户通过“复制当前简历”创建完整副本，再单独修改。

## 目标

- 保存并管理多套完整且相互独立的简历资料。
- 在插件弹窗中快速切换当前用于投递的简历。
- 在设置页中新建、复制、重命名、删除和编辑简历。
- 普通填充、AI 填充、信息侧栏和简历附件始终使用当前简历。
- 无损迁移现有单简历数据。
- JSON 备份与 WebDAV 同步覆盖全部简历和当前选择。

## 非目标

- 不在投递记录中保存或编辑所用简历。
- 不提供简历之间的字段级共享或继承。
- 不在弹窗中提供“管理简历”入口；弹窗只提供切换控件。
- 不对 WebDAV 冲突执行逐简历合并。
- 不改变现有字段检测和表单匹配算法。

## 数据模型

每套简历继续完整复用现有 `UserProfile`：

```ts
interface ResumeProfile {
  id: string;
  name: string;
  createdAt: string;
  updatedAt: string;
  profile: UserProfile;
}

interface ResumeProfileLibrary {
  schemaVersion: 1;
  activeProfileId: string;
  profiles: ResumeProfile[];
}
```

存储新增 `resumeProfileLibrary`。所有 `ResumeProfile.profile` 均为独立完整对象，包括：

- 基本信息；
- 教育经历；
- 实习与工作经历；
- 项目经历；
- 技能与证书；
- 自定义信息；
- 简历原文件及解析文本。

`activeProfileId` 必须指向 `profiles` 中存在的条目。资料库至少保留一套简历。

## 兼容层与消息协议

现有消费方继续使用 `UserProfile`，避免把多简历概念扩散到填充与 AI 链路：

- `GET_USER_PROFILE`：返回当前简历的 `profile`。
- `SAVE_USER_PROFILE`：只更新当前简历并刷新 `updatedAt`。
- `PARSE_RESUME`：解析结果合并到当前简历。

新增资料库操作消息：

- `GET_RESUME_PROFILES`：返回轻量列表和当前 ID，不返回重复的大型附件数据。
- `SWITCH_RESUME_PROFILE`：校验 ID 后更新当前选择。
- `CREATE_RESUME_PROFILE`：创建空白简历并切换到新简历。
- `DUPLICATE_RESUME_PROFILE`：深复制当前简历并切换到副本。
- `RENAME_RESUME_PROFILE`：校验名称后重命名。
- `DELETE_RESUME_PROFILE`：删除指定简历并返回新的当前 ID。

资料库读写和名称规则集中在独立服务中，UI 不直接拼装或修改底层结构。

## 名称与 CRUD 规则

- 新建简历默认名称为“未命名简历”；若重名则顺延为“未命名简历 2”等。
- 复制名称默认使用“原名称 - 副本”；若重名则追加序号。
- 名称保存前去除首尾空白。
- 名称不能为空，且同一资料库内不可重名。
- 复制使用深复制，后续修改副本不得影响来源简历。
- 删除前由 UI 二次确认。
- 仅剩一套简历时禁止删除。
- 删除当前简历后，优先选择原列表中的下一套；没有下一套时选择上一套。

## 旧数据迁移

读取资料库时执行惰性迁移：

1. 若 `resumeProfileLibrary` 合法，直接规范化并使用。
2. 若不存在资料库但存在旧 `userProfile`，将旧资料完整迁移为“默认简历”。
3. 若两者均不存在，创建一套空白“默认简历”。
4. 若当前 ID 无效，修复为第一套有效简历。
5. 迁移成功写入新资料库后保留旧键一个版本周期作为恢复来源；业务写入只更新新资料库，避免双写分叉。

若资料库损坏但旧资料仍合法，允许从旧资料恢复为单套“默认简历”。无法恢复时返回明确错误，不静默覆盖已有原始值。

## 插件弹窗

在现有“当前信息”区域上方增加“当前简历”下拉框：

- 列出全部简历名称并选中当前简历；
- 选择后立即调用切换消息并持久化；
- 切换期间禁用填充按钮，成功后重新读取当前资料；
- 切换失败时恢复原选项并提示错误；
- 不新增“管理简历”入口；用户继续通过现有“设置个人信息”按钮进入设置页。

## 设置页

在现有标签页内容上方增加简历管理栏：

- 显示并切换当前正在编辑的简历；
- 提供“新建空白”“复制当前”“重命名”“删除”；
- 下方继续沿用基本信息、教育经历、实习与项目、自定义信息、简历上传等现有编辑界面；
- 保存按钮只保存当前简历。

设置页维护脏状态。存在未保存修改时切换简历，弹出三项选择：

- 保存并切换；
- 放弃修改并切换；
- 取消。

新建、复制和删除会改变当前简历，执行前同样经过该保护流程。重命名不改变表单数据，可直接完成，但仍需显示操作结果。

## 跨页面同步

弹窗、设置页和信息侧栏监听 `chrome.storage.onChanged` 中的资料库变化：

- 当前 ID 变化时重新读取当前资料；
- 当前简历内容变化时刷新展示；
- 设置页若存在未保存修改，不用外部变化静默覆盖本地表单，而是提示用户重新加载或保留本地修改。

普通填充、AI 扫描填充和 AI 框选补填在每次操作开始时通过 `GET_USER_PROFILE` 获取当前资料，因此切换后无需修改其核心算法。

## 备份与 WebDAV

备份格式升级到 V2，业务数据由单个 `userProfile` 改为完整 `resumeProfileLibrary`，同时继续包含 AI 配置、通用设置和投递记录。

兼容规则：

- 导出 V2 时包含全部简历及当前 ID。
- 导入 V2 时校验资料库结构、唯一 ID、唯一名称和有效当前 ID。
- 导入 V1 时把原 `userProfile` 转换为单套“默认简历”。
- WebDAV 上传使用 V2 完整业务数据。
- WebDAV 下载 V1 时执行同样迁移。
- 同步 hash 包含完整资料库与当前 ID，因此简历内容变化和切换都会触发同步。
- 冲突继续沿用现有整包“使用本地/使用远端”处理，不做字段级或简历级合并。

投递记录的数据结构与界面保持不变。

## 错误处理

- 当前 ID 无效：自动修复为第一套有效简历。
- 名称为空或重复：拒绝操作并返回可展示的错误。
- 复制、创建或保存时存储失败：保留原资料库和原当前选择。
- 删除仅剩的一套：拒绝操作。
- 切换目标不存在：不改变当前选择。
- 备份资料库结构非法：拒绝导入，不覆盖本地数据。
- WebDAV 远端数据非法：沿用现有同步错误状态，不覆盖本地数据。

## 测试策略

### 资料库单元测试

- 从旧 `userProfile` 无损迁移为“默认简历”。
- 无数据时创建空白默认简历。
- 无效当前 ID 自动修复。
- 新建名称自动避重。
- 复制为深复制，修改副本不影响来源。
- 重命名拒绝空名称和重复名称。
- 删除至少保留一套，删除当前简历后选择正确的新当前项。

### 消息与存储测试

- `GET_USER_PROFILE` 返回当前资料。
- `SAVE_USER_PROFILE` 只更新当前简历。
- `PARSE_RESUME` 只更新当前简历和附件。
- 切换失败不改变存储。
- 资料库变化触发自动同步队列。

### UI 测试

- 弹窗显示当前简历并能切换。
- 切换期间填充操作不可用，成功后刷新当前摘要。
- 设置页支持新建、复制、重命名和删除。
- 未保存修改时正确处理保存、放弃和取消三条路径。
- 设置页和信息侧栏响应外部切换。

### 备份与同步测试

- V2 往返保留全部简历、附件和当前 ID。
- V1 导入和远端下载正确迁移。
- 非法 V2 在应用前被拒绝。
- 多简历变化进入 hash，WebDAV 上传、下载和冲突流程保持正确。

### 回归验证

- 运行全部自动化测试。
- 执行 TypeScript 构建和 Vite 构建。
- 验证普通填充、AI 扫描填充、AI 框选补填和信息侧栏仍使用当前 `UserProfile` 兼容接口。

## 验收标准

- 用户可保存至少两套完整且独立的简历资料。
- 用户可在弹窗中切换当前简历，无额外管理入口。
- 用户可在设置页新建、复制、重命名和删除简历。
- 复制后修改副本不影响原简历。
- 所有填充方式、信息侧栏和简历附件都使用当前简历。
- 旧版用户升级后原资料完整保留在“默认简历”中。
- 新旧备份和 WebDAV 同步行为符合兼容规则。
- 投递记录保持现状，不关联简历。
